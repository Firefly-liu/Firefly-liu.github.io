把 OCR 搬上 NPU：从 0.3fps 到 13fps

智能车 OCR RKNN 性能优化 · 约 7 分钟

这是整套系统里最惊险的一次优化：在交车前 2 小时把 OCR 从 CPU 硬跑改成 NPU 推理，帧率从 0.3fps 提到 8~13fps。这一篇记录做对了什么、以及本该早点做什么。

内容来源说明

本页内容全部来自我自己的实践 我的实践，时间跨度是 2026 年 6 月 ~ 8 月。上一届交接时这套 OCR 方案还不存在，是从零做起来的。

0.3 fpsCPU 流式处理
8–13 fpsNPU 推理
20–40×吞吐提升

一、为什么要用 OCR

任务要求识别板面上的文字，并与语音指令给出的大类做匹配判断。用目标检测模型直接认字也能做，但字符数量、字体变化带来的样本需求会爆炸；专门的 OCR 更合适。

二、方案选型

用的是 RapidOCR（PP-OCRv4 系列），拆成两个阶段：

阶段 1

文本检测（det）

在整张图里找出所有文本框。对应模型 ch_PP-OCRv4_det_mobile.onnx。

阶段 2

文本识别（rec）

把每个文本框切出来识别成字符。对应模型 ch_PP-OCRv4_rec_mobile.onnx，外加字表 ppocr_keys_v1.txt。

产物用途
ch_PP-OCRv4_det_mobile.onnxCPU 版文本检测
ch_PP-OCRv4_rec_mobile.onnxCPU 版文本识别
ppocrv4_det.rknnNPU 版文本检测
ppocrv4_rec.rknnNPU 版文本识别
ppocr_keys_v1.txt识别用的字表，必须与 rec 模型配套

三、CPU 版：能跑，但不够用

第一版直接跑 onnx，用流式处理的方式一帧一帧喂进去。结果是约 0.3fps——三秒一帧。车在移动中完全不可用，只能"停稳 → 等结果"。

此时的用法

只能配合"手动触发一次识别"的接口使用，确认车停稳之后再取结果。这在比赛里意味着每识别一次都要浪费好几秒。

四、搬到 NPU 上

思路很直接：把两个 onnx 都转成 rknn，让板子上的 NPU 干活。转换走的就是 YOLO 那一套流程（convert.py + 目标平台 rk3588），关键在于版本对齐：rknn-toolkit2 和 rknn_model_zoo 必须是同一版本，车上搭载的是 2.0.0 Beta。

为什么要多线程

det 和 rec 是两个串行阶段，而且每张图可能有多个文本框需要逐个识别。用多线程把"检测"和"识别"流水线化，才能把 NPU 利用率压满——这是从个位数帧率到十几帧的关键。

五、实际使用方法

启动识别

bash
# 进入 OCR 专用虚拟环境
conda activate rapid_ocr

# 启动识别节点（前提：YOLOv8 节点已经在发布图像话题）
python3 RapidOCR.py

# 纯测试程序：按 s 识别一次，按 q 退出
python3 TEST_OCR.py
启动顺序有依赖

OCR 节点订阅的是 YOLOv8 发布的图像话题，所以必须先启动视觉节点，否则 OCR 拿不到输入图像。

话题接口

话题用途用法
/ocr/trigger手动触发一次识别rostopic pub /ocr/trigger std_msgs/Empty --once
/ocr/text实时查看识别出的文字rostopic echo /ocr/text
/ocr/bbox查看文本框坐标rostopic echo /ocr/bbox

六、相机与外部触发

另一路任务是识别交通灯，需要直接调起相机拍照：

bash
# 调起 USB 相机
roslaunch usb_cam usb_cam-test.launch

# 水平翻转（不同安装角度下需要）
python openMV_摄像头水平翻转.py

# 相机启动后拍照，图片保存在启动目录
相机角度会牵动一串改动

把相机调高之后，必须重新做相机标定。标定一变，找板的偏移量、巡线的阈值都要跟着复核。

七、资源冲突：两个识别抢相机

图像识别和二维码识别会互相冲突。由于当时没有把 C++ 与 Python 整合在一起的方法，采取的办法是进程级切换：

用 Python 调度 launch 文件

用 Python 拉起二维码识别的 launch 文件；一旦检测到二维码，就关闭它、再启动图像识别的 sh 脚本。本质上是用进程生命周期做互斥，简单但有效。

八、识别效果上的几个观察

现象 1

远距离反而能认出来

把远距离拍到的图片喂给模型，能识别；说明字符尺寸不是决定性问题。

现象 2

字被挡住就失败

一旦有遮挡物挡住部分文字，识别直接失败。

现象 3

只喂"被挡住"的样本反而能识别

顺着现象 2 做了个小实验，只喂遮挡样本，确实能识别出来——但代价是靠近了反而认不出来。这说明数据分布被推偏了。

结论

老老实实重新训练

绕不过去。数据要覆盖"近、中、远 + 有无遮挡"的整体分布，不能靠偏方。

九、复盘：本该早点做的事

  1. 先评估推理后端再写业务逻辑。一上手就用 CPU 版 onnx 跑通了流程，却没想到后端的算力完全不够，最后在交车前 2 小时才动手换 NPU。应该在做方案时就先测一遍车端推理帧率。
  2. 把模型转换脚本提前跑通。det 和 rec 两个模型都要转，版本对齐问题会占掉不少时间。
  3. 触发机制比识别精度更重要。比赛里"什么时候拍"往往比"拍得准不准"更影响成功率，手动触发是最稳的兜底。
一句话总结

车端部署的帧率一定要在项目早期就测。同样的模型，CPU 和 NPU 的差距是 20 倍以上，这不是调参能弥补的。
