导航与建图：TF、导航点与局部规划器

智能车 导航 建图 · 约 9 分钟

导航是整套系统里"玄学感"最强的部分：同一份代码，换个场地、换个发车点就不好使。事后复盘，绝大多数所谓玄学其实是坐标系问题。这一篇把踩过的坑按"现象 → 原因 → 处理"整理。

内容来源说明

本页是两届队员接力的成果。按备赛日志的时间线：2025 年 9 月 19 日之前的内容来自上一届交接的日志（前届记录），之后是我自己的实践（我的实践）。

前届记录第一节 发车点铁律、第二节坑 2（里程计与 IMU 冲突）、第五节 dwa/teb、第六节 rosbridge、第七节 降级策略、第八节 联合标定
我的实践第二节坑 1 / 坑 3（TF 打架、多余分支）、第三节 建图、第四节 导航点与航向角

一、先立一条铁律：发车点必须与建图起点重合 前届记录

这条最反直觉，但代价最大

建图时的起点，必须和你实际发车时的起点重合。否则地图整体会相对车身发生偏移，导航点全部"差一步"，表现为车到不了、绕圈、卡墙角。这不是参数问题，调参救不回来。

自检方法很简单：打开 RViz，把雷达点云和地图叠在一起看，两者吻合就对了。这个过程不需要重启底盘，随时可以比对。

二、TF 坐标系：三个真实踩过的坑 前届记录我的实践

坑 1：两条 TF 在「打架」 我的实践

现象是雷达坐标在乱跳，导航表现时好时坏。定位到根因在 sensor_tf_server.py：里面有一段发送激光雷达 TF 变换的代码，本来是应该注释掉的，但不知道为什么被启用了。启用之后 x=0.11 和 x=-0.11 两个变换同时存在，互相覆盖。

python
# sensor_tf_server.py

坑 2：里程计解算与 IMU 冲突 前届记录

建图时车的坐标系呈现一种很诡异的状态，最后确认是底盘控制 launch 里 ekf 配置的问题，把 odom_use 改成 false 就正常了。

坑 3：多余的 TF 分支 我的实践

做定位时会发现"有一条奇怪的 tf 分支没有被使用"。它来自 hector_mapping 的 launch 文件（在 /opt/ros/<版本>/share/hector_mapping/launch/）。这个目录是只读的，需要用 sudo chmod 777 解除，但这属于系统包内文件——改之前先备份到桌面，我改过之后没有生效，最后还是回退了。

三、建图：gmapping 与 hector 我的实践

车上可用的两套建图方案各有优劣，我都装过。启动顺序如下：

bash
# 1. 底盘
roslaunch ucar_controller base_driver.launch

# 2. 雷达
roslaunch ydlidar ydlidar.launch

# 3a. hector 建图
rosrun hector_mapping hector_mapping _use_tf_scan_transformation:=false

# 3b. 或 gmapping 建图
roslaunch ucar_map gmapping.launch

# 4. 键盘遥控走一圈
rosrun teleop_twist_keyboard teleop_twist_keyboard.py

# 5. 保存地图
rosrun map_server map_saver -f /home/ucar/Downloads/ucar_ws/src/地图名
方案特点适用场景
gmapping需要里程计，闭环效果好常规室内建图
hector不强依赖里程计，对雷达频率要求高里程计不准时的备选
建完图必做的两个检查

一是看地图是不是"方的"——如果墙体明显歪斜，说明建图过程中坐标系或雷达有漂移，这张图不能用；二是看自己摆的板子是不是歪的，物理摆放歪了，再准的图也救不回识别效果。

四、导航点与航向角 前届记录我的实践

导航点的输入是一个位姿，需要 x, y, yaw 三个量。有两种确定方式。

方式一：手动示教

把车放到目标位置，先订阅目标话题再手动发布一个导航点，终端就会把该点的横纵坐标与偏航角打印出来，直接抄进代码。

bash
rostopic echo /move_base_simple/goal

方式二：角度换算

导航接口收的是四元数，人工很容易搞错。记住两条：

  • 把获得的四元数转成欧拉角，再看 yaw；
  • 反过来换算时，只改 z 和 w，x、y 保持 0。
别手算

角度和弧度、欧拉角和四元数之间的转换非常容易出错。用在线转换工具算好再粘进去，比手算靠谱得多。

导航点相关的报错

发布导航点时出现过 [move_base-9] 错误，解决办法是把官方导航完整跑一遍，问题会消失。根因是 global_costmap_params.yaml 缺少一段配置，照着官方文件补上即可。

五、局部规划器：dwa 与 teb 的差距 前届记录

据前届记录，这是他们收获最大的一次更换。原本一直用 dwa，导航有极小概率卡墙角；换成 teb 之后立刻能感觉到两者差距。

一个侧面印证

群里有人提到，上一代车受限于算力，用的检测模型只有一两帧的帧率。这说明硬件算力会直接限制算法选择——换规划器之前，先确认车端能不能跑得动。

实时调参工具

导航参数不要靠"改文件 → 重启 → 观察"的循环，用可视化工具直接拖：

bash
rosrun rqt_reconfigure rqt_reconfigure

六、远程遥控：rosbridge 前届记录

需要从电脑、虚拟机、WSL 等不同设备控制小车或接收话题时，用 rosbridge 打通。

步骤 1

两边都安装 rosbridge 功能包

其实下一边也能用，但两边都有会更省事、更灵活。

步骤 2

用 rosbridge_websocket.launch 启动

功能包目录下有三个 launch 文件，用 websocket 那个。默认端口 9090。

步骤 3

谁接收，谁跑脚本

接收端运行 Python 脚本，关键参数是对方的 IP 和端口。

注意

两台设备都开 rosbridge 时

端口会冲突，需要把其中一台的端口改掉（在 /opt/ros/<版本>/share 下对应功能包的 launch 文件里改）。

远程链路的两个典型故障

① 静默断连：接收端在某台设备长时间没有消息后，对方再发就收不到了。处理方式是写一个 5 秒一次的循环定期取一次消息，并放进多线程，同时补上断线重连机制。
② 虚拟机拿不到小车 IP 下的信息：用 NetworkManager 的重启方式临时解决，但这是虚拟机的通病，不是根修——到现场先 ping 一下确认网络层可达。

七、当定位数据不可用时的降级策略 前届记录

地图上有些区域会被标记为"概率无法到达"，原因是雷达数据出现 nan（非数值）。这个问题在前届记录里折磨了很久，最后没有强行修复，而是设计了多级降级：

方案 A

调雷达参数

怀疑是检测范围过小导致 nan；用 rostopic echo 观察实际数据时又看起来正常。

方案 B

怀疑是算角度时分母为 0

雷达数据转角度时，分母存在为 0 的可能。

方案 C（最终采用）

超时跳过 + 标志位

用多线程监听告警消息，一定时间内告警数超过阈值就切到下一个目标点，并设全局标志位记录当前目标点。旋转找板前套一个循环：目标点有效就执行并跳出，无效就去下一个点。

最终兜底

放弃标定，改用 PID 逼近

所有导航点都不可用时，清空当前目标标志位重新找板，并把雷达相机联合标定切换为 PID 逼近。

八、相机与雷达的联合标定 前届记录

标定直接决定"看到的板子在雷达坐标系里的哪个位置"。记录几条经验证的事实：

  • 车坐标系与地图坐标系之间的 tf 没有问题，说明 yaw 是准的；
  • 中心点坐标误差幅度小于 1，可以排除模型本身的问题；
  • anglex 在 4 左右时能正常运行，在 -35 时失败；此时雷达列表索引仍在合法范围内，没有明显证据表明它是关键——因此把排查重点放在路径规划参数上更有效率。
偏移量给反了这件事

如果车总是往反方向偏，先把 x、y 轴上的偏移量打印出来确认正负号——前届日志里有一次就是符号给反了，白调了一整天。

九、调导航的优先级建议

  1. 确认发车点与建图起点重合（最重要，先做）
  2. 确认没有多余的 TF 分支在打架
  3. 确认 ekf 的 odom_use 等里程计配置正确
  4. 换局部规划器（dwa → teb）看整体表现
  5. 最后才是逐个调参数
