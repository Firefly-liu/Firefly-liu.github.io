ROS 环境搭建踩坑实录：双系统、WSL2 与那些年重装过的系统

智能车 ROS 环境搭建 · 约 8 分钟

环境这一关是整段备赛历程里翻车最多的部分。ROS 本身不难，难的是让它在一个稳定的系统上跑起来——前一届为此重装过系统、烧录过 TF 卡、甚至把车寄回去维修；我接手后补上了 WSL2 这条更省事的路线。下面按顺序记录，能帮你少走几周弯路。

内容来源说明

本站的 ROS 技术记录是两届队员接力的成果。按原始备赛日志的时间线划分：2025 年 9 月 19 日之前的内容来自上一届交接的备赛日志，标注为 前届记录；之后是我自己的实践，标注为 我的实践。

前届记录第四 ~ 第九节：装软件的坑、软件源证书过期、远程桌面、网络问题、Gazebo 仿真、命令小抄
我的实践第一 ~ 第三节：方案选型、WSL2 的正确姿势、双系统安装
先说结论

如果你只是想跑 ROS1 仿真和开发，优先用 WSL2，不要碰双系统；如果你必须双系统，Ubuntu 版本选 22.04.5，别用 20.04.6。

一、三种方案怎么选 我的实践

先把三条路摆在一起对比，选错方向的代价是几天甚至一周。

方案优点缺点推荐度
双系统能调用独显，性能最完整安装易翻车、分区风险高、切换要重启只在必须用 GPU 做仿真实时检测时考虑
WSL2启动快、切换快、可调用独显、不碰分区没有图形化桌面，初次上手难受；吃 C 盘空间首选
虚拟机最安全，删了不心疼调不了独显；网络经常抽风备用

二、WSL2 的正确姿势 我的实践

WSL2 装 Ubuntu 的版本选择很关键：用 ROS1 就只能选 20.04，别听网上教程一律让你上 22.04 / 24.04。

powershell
# 列出可安装的发行版，从里面复制带 Ubuntu-20.04 的那个名字
wsl --list --online

# 用完整名字安装
wsl --install Ubuntu-20.04
磁盘预留

WSL2 的虚拟磁盘会随使用膨胀，建议 C 盘预留 200GB 以上。装完先去确认剩余空间，别等编译到一半磁盘满了。

三、双系统安装：20.04.6 是个坑 我的实践

用 ubuntu-20.04.6-desktop-amd64.iso 安装时，安装器会因为软件源证书过期而失败。换成 ubuntu-22.04.5-desktop-amd64.iso 就可以正常装完。

安装界面显示不全

按住 Win 再用鼠标拖动窗口，可以把被裁掉的"下一步"按钮拖出来。

启动盘工具怎么选 我的实践

工具评价
Rufus推荐，稳定可靠
UltraISO备选
balenaEtcher备选
Win32DiskImager不建议
Ventoy2Disk不建议
DiskGenius不建议

另外，启动盘最好放一块独立的物理硬盘，不要和系统盘共用一块盘。

ROS1 装在 Ubuntu 22.04 上 我的实践

20.04 是最后一个原生支持 ROS1 的版本，所以 22.04 上直接跑"一键安装脚本"是不行的，需要参考社区给出的 ROS1 on 22.04 方案手动处理。

四、装软件的正确姿势 前届记录

这是最容易被网上教程带偏的部分。先记住四种包格式对应的命令：

bash
# deb 包
sudo dpkg -i 安装包名.deb

# sh 脚本
sh 安装包名.sh

# whl 包（一定带国内源，否则慢到怀疑人生）
pip install 安装包名.whl -i https://pypi.tuna.tsinghua.edu.cn/simple

# zip 压缩包
unzip 压缩包名.zip
不要随便用「一键换源 / 一键安装」脚本

前届日志里遇到过一次一键脚本把系统软件源改得面目全非、最后把系统装废的情况。装 VS Code 这类软件请去官网下 deb 包，而且不要装最新版——前届用的是 1.83.1。

常用体检命令 前届记录

目的命令
查看磁盘占用（千万别满）df -h
查看 Python 版本python --version
查看 IP（远程连接用）ifconfig
查看系统架构uname -m
以 root 强制删除（破坏性极高）sudo rm -rf /路径

五、ROS1 软件源证书过期 前届记录

遇到软件源证书过期时，有两种处理方式。第一种是应急：临时绕过签名验证。

bash
# 应急：允许更新源 / 安装时忽略认证（不是长久之计）
sudo apt update --allow-insecure-repositories
sudo apt install --allow-unauthenticated 包名

第二种是正式修复：删掉旧密钥，重新拉取新的。

bash
# 用短 ID（后 8 位）删除旧密钥
sudo apt-key del AB17C654

# 重新获取完整密钥
sudo apt-key adv --keyserver keyserver.ubuntu.com --recv-keys F42ED6FBAB17C654

六、远程桌面 前届记录

车端用的是 NoMachine，装 armv8 版本的包。它的能力比想象中强，甚至支持"主机复制、车端粘贴"。

两个坑

第一，安装时不要勾输入密码下面那个复选框；第二，安装路径里不要有中文。前届因为这两点重装过好几次。

七、网络问题 前届记录

Ubuntu 有时会表现为"没有网络"，连网络标识都不显示。下面这组命令是有效的临时解法：

bash
service NetworkManager stop
sudo rm /var/lib/NetworkManager/NetworkManager.state
service NetworkManager start

另外，虚拟机 ping 不通小车，往往也是同一类问题。这属于虚拟机的通病，不是长久修复，到了现场先 ping 一下确认网络层是否可达即可。

车端首次配置顺序 前届记录

第一步

下载 NoMachine（armv8）并导入功能包

先解决"看得见、点得动"的问题，后面所有操作都在远程桌面上完成。

第二步

编译之前先换源

推荐用国内镜像源，否则 apt 和 pip 的等待时间会让人放弃。

第三步

编译，报错就查

catkin_make 阶段的报错基本都能靠补装依赖解决。

第四步

配置环境变量

功能包的环境变量一定要放在 ~/.bashrc 的最底部，否则会被前面的语句覆盖。

八、Gazebo 仿真 前届记录

Gazebo 的问题主要集中在 Python 版本与 tf 包的冲突上，典型报错长这样：

spawn_model 报错
ImportError: dynamic module does not define init function (init_tf2) File ".../gazebo_ros/spawn_model", line 36, in <module> from tf.transformations import quaternion_from_euler

解法是让 Python3 能正常使用 ROS 的 tf。解决之后如果仿真建图在 RViz 里不显示，可以先查建图相关节点的话题与坐标系，而不是急着重装。

被要求重装 Gazebo 的那一天

重装确实解决了问题，但要记住：仿真环境的问题，先确认是"没数据显示"还是"数据发错了坐标系"，两者的排查方向完全不同。
